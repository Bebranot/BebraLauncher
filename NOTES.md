## Архитектурные решения

- Игру запускает `SS14.Loader.exe` (.NET 10), а не лаунчер; Rust-ядро Loader заменить не может. Принят вариант «собирать Loader из исходников официального лаунчера» (`loader/`, MIT). Почему так — `docs/protocol.md`, раздел 9.
- Схема `content.db` совпадает с официальным лаунчером: Loader читает её напрямую. Не менять.
- Токены не попадают в UI: `AccountRow` содержит только id, имя, срок и состояние. Пароль идёт по IPC только в `login` и сразу на auth-сервер.
- `ss14://` и `ss14s://` (в том числе redial) только выбирают сервер и показывают баннер; подключение — по кнопке «Играть». Официальный лаунчер подключается сразу. Это сознательное отличие. Регистрация схем — `HKCU\Software\Classes`, опция в настройках, по умолчанию выключена (`system.rs`).
- Текстовые пакеты: принимаются только `Locale/<culture>/*.ftl`; если в пакете есть любой другой файл, отклоняется весь пакет (`core::packs`).
- Моды (`.dll`) — это исполнение стороннего неподписанного кода в процессе игры. Защита только по SHA-256 из `patches/manifest.json`; автор и подпись не проверяются. Сервер может счесть моды читерством — об этом сказано в UI и README.
- Палитры тем скопированы из MusyaLoader (AGPL). Для публичного релиза нужна отдельная проверка лицензии.

## Протокол и сеть

- Хаб отдаёт поля сверх модели официального лаунчера 0.40.1 (`map`, `preset`, `round_id`, `panic_bunker`, `inferredTags`). Парсер мягкий: без `deny_unknown_fields`, все поля `statusData`, кроме `players`, опциональны.
- Порт по умолчанию: `ss14://` — 1212, `ss14s://` — 443 (`addr.rs`).
- `/info` серверов из хаба берётся через хаб (`api/servers/info?url=`) и работает, даже если сервер недоступен напрямую. Но подключение всё равно требует `/info` у самого сервера (так делает и официальный лаунчер): недоступный напрямую сервер не подключится (проверено на eridani).
- Прямой `/status` может не ответить за 5 с. Это штатный Offline, а не ошибка.
- У всех базовых URL (хаб, auth, CDN) есть fallback-зеркало. Второй URL стартует через 3 с (`http.rs`, `ATTEMPT_DELAY`), поэтому POST логина может уйти на оба зеркала, как и у официального лаунчера.
- Заголовок `SS14-Launcher-Fingerprint` не отправляем (решение владельца). Если auth начнёт отклонять вход без него, вернуться к вопросу.
- Размеров файлов в манифесте нет, поэтому размер delta-загрузки заранее неизвестен. Прогресс считаем по блобам, оценку не выдаём за точную.
- Не проверять размер запросом с `Range` и не делать `GET` на zip ради проверки: CDN игнорирует Range и отдаёт весь файл (`curl -r 0-0` качал 209 МБ до таймаута). `HEAD` на `client.zip` даёт 405.
- Версия модуля: максимальная `ver ≤ engine_version`, суффиксы вроде `-fix-physics` отбрасываются. Официальный лаунчер на таких версиях падает в `System.Version.Parse`, это наше отличие. Модули на живом сервере не проверены (у тестового сервера их нет).
- Движок с `insecure: true` не запускается; `redirect` — это цепочка версий (`264.0.2-fix-physics` → `264.0.7-fix-physics`).
- Манифестный режим проверен живьём, включая delta-обновление (сервер выкатил новый билд, лаунчер докачал только новое). Zip-режим и ACZ на живом сервере не проверены: все проверенные серверы имеют манифест.
- Загрузка блобов идёт в одной SQLite-транзакции. При обрыве готовые блобы сохраняются в `InterruptedDownload` и подхватываются при следующей попытке. Обрывки старше 7 суток удаляются при cull.

## Подпись и доверие

- Ed25519 проверяется дважды: ядро сразу после скачивания (движок и модули), Loader — при каждом запуске (engine-zip). Официальный лаунчер sha256 движка не проверяет. Наш `signing_key` идентичен upstream.
- Ядро также содержит `signing_key_multiverse.pem` и `signing_key_supermatter.pem` и выбирает ключ по имени движка (`signature.rs`, `launch.rs`). Происхождение этих ключей в документации не описано.
- Выключателя подписи в Loader нет: `SS14_DISABLE_SIGNING` удалён, а `launch.rs` убирает эту переменную из окружения клиента. Не возвращать.
- Подпись не покрывает патчи `.dll` (см. «Архитектурные решения»).
- Самообновление: Ed25519 над строкой `bebra-update:<версия>:<sha256 установщика>` (`self_update.rs`). Публичный ключ вшит (`update_key.pem`). Закрытый ключ только у владельца: `%USERPROFILE%\.bebra\update-signing.key`. Он не попадает в git (`*.key` в `.gitignore`). При потере ключа придётся вручную поставить версию со сменой ключа.
- Репозиторий закрытый: без GitHub-токена (Contents: read) `releases/latest` даёт 404. Токен лежит в Credential Manager, цель `BebraLauncher/github-token`.
- Выпуск: `scripts/release.ps1` (нужен `GITHUB_TOKEN` с правом записи; `-DryRun` собирает и подписывает без публикации). Ни одного релиза на 2026-10-04 не публиковалось, живой цикл «скачать и поставить» не проверен.
- Самообновление проверяет релизы через 8 с после старта и далее каждые 4 ч; установка при закрытии (`RunEvent::Exit`). В debug-сборке установка отключена.

## Аккаунты

- Пароль не хранится и не логируется. Токен — Credential Manager, цель `BebraLauncher/account/<userId>`, Persist=LOCAL_MACHINE, blob — JSON (user_id, username, token, expire_time), лимит 2560 байт. Любой процесс того же пользователя может его прочитать; это не сильнее самой учётной записи Windows.
- Токен попадает клиенту только через env `ROBUST_AUTH_*` и только если `auth.mode != Disabled` и аккаунт выбран. В лог команда запуска пишется без значений env.
- Продление, если до истечения меньше 15 суток (`REFRESH_THRESHOLD`). Сетевая ошибка не означает мёртвый токен, пока он не истёк по времени. Ответ 401 на refresh или ping — токен мёртв.
- `token_refresh_lock` (`game.rs`) не даёт login/logout/select гоняться с продлением.
- Гость: при `auth.mode=Disabled` или без выбранного аккаунта имя `JoeGenero` (`FALLBACK_USERNAME`).
- Живьём проверено 2026-10-03: вход через `bebra login`, ping с мусорным токеном даёт 401, подключение к серверу с `auth.mode=Required`.

## Запуск игры

- Loader сам пишет и удаляет строку в `RunningClient` и держит read-транзакцию на `content.db`. Cull считает клиент живым, если есть строка `RunningClient`, PID жив и путь exe совпадает. Loader проверяет `SQLITE_DONE` при записи строки, иначе живой клиент будет считаться мёртвым.
- Cull: не больше 15 версий всего и 3 на один форк (`cull.rs`). Версию живого клиента не трогать. «Очистить всё» запрещено, пока клиент запущен.
- Клиент при ошибке подключения остаётся открытым (строка `RunningClient` жива), пока пользователь не закроет окно.
- `--launcher` подразумевает `--connect`. Без `build.engine_version` и `manifest_hash` клиент не подключается к новым CDN.
- Из пользовательских аргументов проходят только `--cvar name=value`; `--connect-address`, `--username`, `--ss14-address` отбрасываются (`safe_extra_args`).
- Redial: Loader запускает `<exe> --commands :RedialWait R<hex> C<hex>`, путь берётся из `SS14_LAUNCHER_PATH`. Команду принимает плагин single-instance. Вживую не проверено: нужен сервер, который шлёт redial.
- Время игры и история пишутся только когда игра реально стартовала (событие `Running`). Незаконченные сессии лежат в `active_sessions.json` (`sessions.rs`).

## Настройки и файлы

- Данные лежат в `%LOCALAPPDATA%\BebraLauncher` (`content.db`, `engines\`, `modules\`, `patches\`, `overlays\`, `logs\`). Это отдельно от официального лаунчера.
- Новые поля `settings.json` объявляются с `#[serde(default)]`, санитайзинг — в `Settings::sanitized`.
- При повреждённом `settings.json` берётся `.bak`, а битый файл переименовывается в `settings.json.corrupt-<ts>` (`settings.rs`).
- `merged_from_ui` сливает настройки в Rust, поэтому UI не затирает `favorites` и `history`. `hwid_current` и `hwid_previous` пишет только лаунчер.
- `last_account`: `None` — не выбирал, `""` — гость явно, иначе user id.
- Лог `logs/launcher.log` ротируется при 1 МБ (`applog.rs`).
- После живых тестов откатить историю и `last_account` в `settings.json` (там могут остаться записи).

## HWID

- Зачем: серверы различают компьютер по HWID, а вычисленный движком идентификатор иногда непригоден (подтвердил админ сервера).
- `hwid.rs`: 32 случайных байта дают `legacy` (64 hex) и `modern` (`00` + те же байты, 66 hex). Они передаются в `BEBRA_HWID_LEGACY` и `BEBRA_HWID_MODERN`.
- Патч `loader/Bebra.HwidPatch/` (Harmony) постфиксит `GetLegacy` и `GetModern`. Файл `Bebra.HwidPatch.dll` ищется рядом с `SS14.Loader.exe`. Если HWID задан, а файла нет, лаунчер пишет об этом в UI, а игра показывает HWID машины.
- Типы движка в патче ищутся по имени, а не ссылкой: смена версии Robust не ломает сборку патча.
- `hwid_auto` включён по умолчанию: новый идентификатор перед каждым запуском.
- Не проверено: смена HWID на живом сервере.

## Сборка и инструменты

- Проверки: `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, в `app/`: `pnpm check`, `pnpm test`. Это же делает CI.
- HTTP-клиент на `native-tls` (SChannel), а не `rustls`: в reqwest 0.13 фича `rustls-tls` переименована в `rustls` и тянет aws-lc-rs, которому на Windows нужны NASM/cmake.
- Тест клиента без подключения: `bebra launch <ss14s://...> --no-connect` открывает главное меню клиента. На lizard гостем не войти (`auth.mode=Required`), поэтому для входа на сервер нужен аккаунт.
- `tauri::generate_context!` требует `app/dist`: для `cargo check` сначала `pnpm build`.
- `cargo build -p bebra-app` без Tauri CLI не вшивает фронтенд: окно грузит `127.0.0.1:1420`. Для проверки UI — `pnpm dev` и debug exe; вшивает только `pnpm tauri build`.
- `tauri.conf.json`: `bundle.active=false`. Релизные настройки в `tauri.release.json`, иначе `cargo check` требует собранный Loader.
- Capabilities: только `core:event:allow-listen` и `allow-unlisten`. CSP строгая (`default-src 'self'`, `connect-src` только ipc). Свои команды доступны без capability.
- Loader: `NU1902`, `NU1903`, `NU1904` — ошибки сборки (`loader/Directory.Build.props`). CI проверяет пакеты отдельным job'ом. `SQLitePCLRaw.lib.e_sqlite3` не ниже 2.1.14 из-за GHSA-2m69-gcr7-jv3q.
- Установщик: `scripts/build-release.ps1` собирает NSIS (около 34 МБ). Loader self-contained (около 96 МБ в ресурсах) проверен: клиент доходит до главного меню.
- `.gitattributes` (`eol=lf`) нормализует переводы строк при коммите. `rustfmt.toml` задаёт `max_width` и `newline_style`.
- `app/package.json`: `packageManager: pnpm@10.0.0`.
- Иконка приложения — заглушка («B» на градиенте, `app/src-tauri/icons/source.png`).
