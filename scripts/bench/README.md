# Замеры клиента

Инструмент разработчика, с лаунчером не поставляется. Запускает клиент с заданным профилем против локального сервера, снимает кадры на одной и той же сцене и пишет JSON-отчёт на каждый прогон.

- `loader/Bebra.BenchPatch` — патч в клиент: считает кадры, GC, память, сам ведёт по маршруту и закрывает игру.
- `run-bench.ps1` — прогоняет план по кругу (A B C A B C), чтобы дрейф машины задевал все варианты одинаково.

## Подготовка

1. Соберите клиент и сервер игры в Release: в Debug числа не имеют смысла.
2. Запустите сервер на отдельном порту, карта должна быть постоянной.
3. Опубликуйте загрузчик и положите патчи рядом с ним:

```bash
dotnet publish loader/SS14.Loader/SS14.Loader.csproj -c Release -r win-x64 --self-contained -o <папка>
```

```bash
dotnet build loader/Bebra.BenchPatch/Bebra.BenchPatch.csproj -c Release -o <папка для сборки патча>
```

То же для `Bebra.PerfPatch`. Нужны `Bebra.BenchPatch.dll` и `Bebra.PerfPatch.dll` рядом с `SS14.Loader.exe`.

4. Соберите CLI: `cargo build --release -p bebra-cli`.

Клиент пишет настройки в `%APPDATA%\Space Station 14\data\client_config.toml`. Перед замерами сохраните этот файл и верните его после.

## План

JSON, ключ — имя варианта:

```json
{
  "balanced": { "profile": "balanced" },
  "weak": { "profile": "optimized", "affinity": 3, "env": ["DOTNET_gcServer=0"] },
  "uncapped": { "profile": "optimized", "vsync": false },
  "custom": { "profile": "custom", "switches": ["ao_off"], "cvars": ["light.blur=false"] }
}
```

- `vsync: false` снимает и VSync, и предел кадров, чтобы мерить запас. Без этого поля профиль остаётся таким, как у игрока.
- `affinity` — маска ядер. Скрипт применяет её заново каждые 5 секунд, потому что при открытии окна маска клиента сбрасывается. Лаунчер при этом всё равно видит все ядра, поэтому Server GC надо выключать явно.

## Запуск

```powershell
scripts/bench/run-bench.ps1 -PlanFile plan.json -OutDir runs/a -Loader <папка>/SS14.Loader.exe -Server ss14://localhost:1213 -DataDir <папка данных> -Repeats 2 -Warmup 30 -Seconds 48 -Tour '@8 24;@8 8;@24 -24' -Anchors 'port bow|-49.5|18.5|starboard quarter|76.5|-62.5'
```

- `-Tour` — команды консоли через `;`. Запись `@x y` означает точку в координатах грида: станция встаёт с случайным поворотом, поэтому патч сначала калибруется по двум варп-точкам из `-Anchors`.
- Шаг маршрута задаёт `BEBRA_BENCH_TOUR_STEP` в секундах.
- `-Setup` выполняется один раз перед замером, например спавн толпы. Сущности остаются на сервере до его перезапуска.
- Готовые отчёты пропускаются, поэтому прерванную серию можно запустить снова.

## Как читать отчёт

- `frame_ms` (`p50`, `p99`, `worst_1pct_avg`, `max`), `stutters_over_33ms`, `stutters_over_50ms` — плавность. По ним и надо сравнивать, средний FPS скрывает рывки.
- `render_ms`, `update_ms`, `tick_ms` — куда уходит кадр. `render_ms` включает ожидание VSync.
- `gc_gen0/1/2`, `gc_pause_ms` — сборка мусора за время замера.
- `private_mb` — выделенная память. `working_set_mb` может резко упасть, если Windows урезала рабочий набор: одному значению не верьте.
- `runtime` и `cvars` показывают, что реально применилось. Сверяйте их первым делом.
- `gpu_3d_percent` без предела кадров делите на FPS. С пределом он ненадёжен: видеокарта снижает частоту, и процент растёт.

## Ограничения

- Слабый процессор эмулируется маской ядер, но частота и кэш остаются прежними.
- Слабую видеокарту и малый объём памяти так не воспроизвести.
- Маршрут снят за призрака: нет поля зрения и своего персонажа, поэтому нагрузка на свет выше, а игровая логика беднее обычной.
- Различия меньше 5% при одном прогоне считайте шумом.
