# Код-ревью BebraLauncher

Дата: 2026-10-29. Ревизия: `main`, коммит `2e72d6a`, версия `0.3.0`.
Область: весь репозиторий — Rust-ядро, Tauri-бэкенд, Svelte-UI, C#-Loader, скрипты сборки/релиза, CI, конфигурация и документация.

Документ только фиксирует проблемы. Код не менялся.
Известные задачи из `docs/IMPROVEMENTS.md` не переписаны заново: они либо подтверждены ссылкой «подтверждает Fxx», либо дополнены тем, чего в том документе нет.

## 1. Главное

1. **Токен аккаунта можно увести на чужой auth-сервер** нестандартным полем `auth.login_urls` из `/info` (P0-1). Официальный лаунчер такого поля не знает; мы его реализовали и передаём туда `ROBUST_AUTH_TOKEN`.
2. **Повреждённый engine-zip не чинится никогда**: после успешной повторной загрузки код выбрасывает проверенную копию и оставляет битую (P0-2). Игра перестаёт запускаться без возможности восстановления из UI.
3. **Патчи — это исполнение неподписанного кода**, а README/PRODUCT обещают обратное. Плюс `SS14_LOADER_PATCHES` не вычищается из окружения, поэтому «выключенные» моды возвращаются после redial (P1-2, P1-3).
4. **Сборка уже красная**: `cargo fmt --check` падает, а CI не собирает C#-Loader вообще. Уязвимая native-SQLite 2.1.10 едет в установщик (P1-4, P1-40, P1-41).
5. **Три «залипающих» состояния**: восстановленные PID навсегда блокируют очистку и автообновление (P1-17); холодный старт теряет `ss14://` и redial (P1-18); битый `settings.json` может сделать окно пустым, потому что санитайзер не применяется при чтении (P1-19).
6. **UI местами не соответствует PRODUCT.md**: светлая тема на фоне «космос» нечитаема (P1-23), «Новости» при ошибке зацикливают запросы (P1-24), «Моды» не прокручиваются (P1-25), а настройки перечитывают обои на каждое нажатие клавиши (P1-30).

## 3. P0 — критично

### P0-1. Сервер может увести токен аккаунта на свой auth-сервер

**Где:** `crates/core/src/server.rs:87-94`, `crates/core/src/play.rs:222-238`
**Что:** в модели `/info` есть нестандартное поле `auth.login_urls`. Оно подставляется в `AuthEnv.auth_server_url`, а тот уходит клиенту как `ROBUST_AUTH_SERVER` вместе с `ROBUST_AUTH_TOKEN`:

```rust
let effective_auth_server = if let Some(urls) = &info.auth.login_urls {
    urls.first().cloned().unwrap_or(default_auth_url)
} else { default_auth_url };
```

Официальная модель `SS14.Launcher/Models/ServerInfo.cs` (проверено по upstream `master`) содержит только `mode` и `public_key`; поля `login_urls` там нет. То есть его добавили мы, и никакой проверки схемы/хоста/принадлежности к Wizards' Den нет.
**Почему:** клиент предъявляет токен тому URL, который назвал сервер. Достаточно ответа `/info` с `"login_urls":["https://evil.example/"]`, чтобы получить токен игрока. При `via_hub` поле приходит ещё и через хаб.
**Исправить:** удалить поле и ветку; всегда использовать `AuthClient::most_successful_url()`. Если фича нужна для сторонних auth-серверов — разрешать только `https` и только из явного allowlist, иначе игнорировать с записью в лог. Тест: `/info` с `login_urls` не меняет `ROBUST_AUTH_SERVER`.
**Уверенность:** высокая, что код так работает; эксплуатация требует, чтобы сервер прислал нестандартное поле (сейчас таких серверов, вероятно, нет).

### P0-2. Повреждённый engine-zip не чинится: проверенная загрузка выбрасывается

**Где:** `crates/core/src/engine.rs:230-245`, `crates/core/src/engine.rs:263-275`
**Что:** если `engines/<ver>.zip` уже существует, но SHA-256 не совпал, начинается повторная загрузка. После успешной проверки выполняется:

```rust
if !zip.is_file() {
    if let Err(e) = std::fs::rename(&part, &zip) { ... }
} else {
    let _ = std::fs::remove_file(&part);   // проверенная копия удалена
}
std::fs::write(&sig, &resolved.sig)?;      // подпись — к выброшенному файлу
```

Ветка `else` удаляет только что скачанный `.part` и оставляет старый битый zip. Затем записывается подпись, соответствующая удалённому файлу.
**Почему:** состояние «битый zip» становится неисправимым из лаунчера. Каждый Play заново тянет 7–8 МБ, выбрасывает результат и возвращает `downloaded: true`; Loader получает zip, не соответствующий подписи, и выходит с кодом 2. Пользователь видит «игра не запускается» без причины и без выхода.
**Исправить:** всегда заменять целевой файл проверенным: удалить/переименовать старый, затем `rename(part, zip)`; `.sig` писать только после успешной замены и через temp+rename. Тест: в `engines/9.9.9.zip` лежит мусор → после `install_engine` файл совпадает с загруженным и подпись валидна.
**Уверенность:** высокая (по коду). Достижимость — низкая/средняя: порча диска, ручная правка, перезаливка версии на CDN.

## 4. P1 — серьёзно

### P1-1. Неидемпотентные POST уходят на два зеркала, а 5xx считается «победой»

**Где:** `crates/core/src/http.rs:120-160`, `crates/core/src/auth.rs:154`, `crates/core/src/auth.rs:201-218`
**Что:** `UrlFallbackSet::send` через 3 с запускает второй URL и возвращает первый **любой** HTTP-ответ, увеличивая счётчик успехов до проверки статуса. Через этот же механизм идут `POST api/auth/authenticate` и `POST api/auth/refresh`.
**Почему:** (1) refresh одного токена может уйти дважды; если сервер ротирует токен, второй запрос инвалидирует токен, который вернул первый, а в Credential Manager сохранится уже мёртвый. (2) `500`/`503` от основного зеркала отменяет запрос к fallback. (3) `most_successful_url()` может выбрать зеркало, которое стабильно отвечает ошибкой, и оно уедет клиенту как `ROBUST_AUTH_SERVER`.
**Исправить:** для POST — только последовательные попытки после транспортной ошибки/таймаута; «победой» считать `2xx` (для auth допустим `401`), иначе продолжать гонку; счётчик успехов инкрементировать только на успешный статус. Тест: первый мирор отдаёт 500 → ответ второго; два параллельных refresh → один POST.
**Уверенность:** высокая по механике; влияние ротации токена — вероятно.

### P1-2. Моды — исполнение неподписанного кода, документация утверждает обратное

**Где:** `loader/SS14.Loader/PatchManager.cs:31-75`, `:240-275`; `app/src/lib/ModsTab.svelte`; `README.md:18`; `PRODUCT.md:36`
**Что:** `SS14_LOADER_PATCHES` разбирается по `;`, каждый путь грузится через `AssemblyLoadContext.Default.LoadFromAssemblyPath` без SHA-256, подписи и проверки владельца. UI умеет устанавливать `.dll`. При этом README обещает, что пакет «меняет слова, но не игру», а PRODUCT — «без возможности исполнения стороннего кода».
**Почему:** это исполнение чужого кода в процессе игры с правами пользователя; каталог патчей доступен любой программе того же пользователя. Главное — обещание продукта неверно, а функция самая рискованная.
**Исправить:** минимум — хранить SHA-256 каждого патча, сверять перед запуском, показывать предупреждение «неподписанный код, сервер может счесть это читерством», индикатор «патчи активны» и кнопку «отключить все» (F13). Максимум — Ed25519-подпись манифеста. README/PRODUCT привести в соответствие.
**Уверенность:** высокая.

### P1-3. `SS14_LOADER_PATCHES` не вычищается — выключенные моды продолжают грузиться

**Где:** `crates/core/src/launch.rs:19-36` (`CLEARED_ENV`), `launch.rs:344-352`; `loader/SS14.Loader/RedialApi.cs:14-37`
**Что:** список очищаемых переменных содержит `ROBUST_AUTH_TOKEN/USERID/PUBKEY/SERVER`, но не `SS14_LOADER_PATCHES` и не `ROBUST_AUTH_SERVERS`, который мы сами же выставляем. Redial запускает лаунчер как дочерний процесс игры, и тот наследует env.
**Почему:** после redial гость/запуск без патчей получает унаследованный `SS14_LOADER_PATCHES`, и «выключенные» моды снова активны. Это прямо противоречит критерию F13 «отключение всех возвращает чистый запуск».
**Исправить:** добавить обе переменные в `CLEARED_ENV` и в `EnvVarsToClear` Loader'а; тест: гостевая команда не содержит `SS14_LOADER_PATCHES`.
**Уверенность:** высокая, что переменная не чистится; цепочка redial → наследование — вероятно.

### P1-4. В поставке уязвимая native-SQLite (NU1903, HIGH)

**Где:** `loader/Directory.Packages.props:9`, `loader/SS14.Loader/obj/project.assets.json:1474-1486`
**Что:** `SQLitePCLRaw.bundle_e_sqlite3` = `2.1.10`; restore сам пишет `NU1903`: «известная уязвимость GHSA-2m69-gcr7-jv3q, уровень серьезности: высокий». По OSV уязвимы версии 2.1.4–2.1.11, исправление — 2.1.12+ (проверить совместимость с `Microsoft.Data.Sqlite.Core`).
**Почему:** Loader открывает `content.db`, содержимое которой построено из данных сервера; HIGH-уязвимость в нативном коде уезжает всем пользователям. CI C# не собирает, поэтому предупреждение никто не увидит.
**Исправить:** поднять до 2.1.12+, добавить `<WarningsAsErrors>NU1903;NU1902;NU1904</WarningsAsErrors>`, проверять `dotnet list package --vulnerable --include-transitive` в CI, обновить NOTES.md:56/84.
**Уверенность:** высокая (версия и предупреждение — из файлов; диапазон исправленных версий — по OSV, сам не перепроверял).

### P1-5. Write-транзакция SQLite удерживается через сетевые `await`

**Где:** `crates/core/src/download.rs:241`, `:306-313`; `crates/core/src/zipmode.rs:62-70`
**Что:** `db.begin()` (BEGIN IMMEDIATE) вызывается до `read_files(...).await`; коммит — раз в 32 МБ, в zip-режиме — одна транзакция на весь ingest (~200 МБ).
**Почему:** на медленном канале write-lock висит десятки секунд/минуты. Loader при старте пишет `RunningClient`; если в этот момент лаунчер (второй процесс, CLI, «Очистить всё») держит блокировку, старт игры может упасть с «database is locked». WAL раздувается на размер транзакции.
**Исправить:** не держать транзакцию через `await`: накапливать готовые блобы и открывать короткую транзакцию только на INSERT, либо коммитить по файлу/небольшими пачками. В zip-режиме коммитить пачками, как в manifest-режиме.
**Уверенность:** высокая по механике; вероятность сбоя зависит от канала.

### P1-6. У скачивания нет таймаута на тело

**Где:** `crates/core/src/download.rs:73-103`; `crates/core/src/http.rs:34-49`
**Что:** у клиента только `connect_timeout(10s)`; `download_to_file` не ставит ни общий, ни idle-таймаут. `MANIFEST_TIMEOUT` применяется только к манифесту и OPTIONS.
**Почему:** сервер, отдавший заголовки и замолчавший, оставляет `stream.next()` навсегда: ни ошибки, ни ретрая, ни fallback (движок/zip качаются с одного URL). Прогресс замирает на 37% без объяснения.
**Исправить:** `read_timeout`/idle-timeout 30–60 с вокруг `next()`, общий лимит размера по `Content-Length` и счётчику байт.
**Уверенность:** высокая.

### P1-7. Размер из сетевого потока управляет аллокацией до 2 ГБ

**Где:** `crates/core/src/download.rs:282-291`, `:339-348`
**Что:** `len` — `i32` из потока (до 2 147 483 647); `zstd::bulk::decompress(&packed, len)` сразу выделяет `len`, несжатая ветка делает `take(len)`.
**Почему:** `len` приходит от игрового сервера, а не из проверенного манифеста (размеров там нет). Один POST с `uncompressedLength = i32::MAX` — дешёвый способ уронить лаунчер по памяти.
**Исправить:** потолок на файл (например, 512 МБ) и потоковая декомпрессия с проверкой накопленного размера вместо `bulk::decompress` с внешней ёмкостью.
**Уверенность:** высокая.

### P1-8. Zip-режим: нет проверки путей и общего бюджета распаковки

**Где:** `crates/core/src/zipmode.rs:93-110`
**Что:** `entry.name()` попадает в `ContentManifest.Path` без проверки (`..`, абсолютные пути, `\`, `:`, NUL, дубликаты). Лимит `MAX_ENTRY_BYTES = 2 GiB` действует на один файл; общего бюджета нет, файл читается целиком в `Vec`, затем сжимается zstd.
**Почему:** сейчас пути из БД никуда на диск не пишутся (Loader читает виртуальную ФС), поэтому это не path traversal «сегодня». Но: дубликат пути даёт сырую SQL-ошибку `UNIQUE constraint failed` посреди установки; 65 535 записей с высоким коэффициентом сжатия — OOM/заполнение диска; любой будущий код, который начнёт писать по этим путям, получит дыру. В `modules::unpack_zip` проверка есть — здесь её забыли.
**Исправить:** валидировать путь той же функцией, что для модулей (все компоненты `Normal`, без `\\`, ведущего `/`, `:`), ввести общий бюджет (`sum(size)` + запас на WAL), читать потоково, дубликаты отбрасывать с понятной ошибкой.
**Уверенность:** высокая по коду; эксплуатация не проверялась.

### P1-9. Гонка установки модуля между процессами

**Где:** `crates/core/src/modules.rs:236-245`, `:269-274`
**Что:** имя `.part` не содержит pid/времени (`module-<name>-<version>.zip.part`), а `install_module` безусловно делает `remove_dir_all(dir)` перед распаковкой.
**Почему:** приложение поддерживает параллельные клиенты, CLI можно запустить рядом. ### P1-10. Cull считает «не удалось проверить процесс» мёртвым процессом

**Где:** `crates/core/src/process.rs:7-27`, `crates/core/src/content_db/cull.rs:44-64`, `:82-93`

### P1-11. Блокирующий IO/CPU внутри async: отмена и прогресс «замирают»

## 7. Что проверено и в порядке

Чтобы следующий диалог не искал это заново:

- **Тесты и статика:** 199 Rust-тестов, 71 UI-тест, `clippy -D warnings` — зелёные; `svelte-check` — 0 ошибок/0 предупреждений. (`cargo fmt` — нет, см. P1-40.)
- **Секреты:** `Token` не реализует `Display`, `Debug` скрыт; в argv токен не попадает; ошибки auth не содержат тела ответа; `Authorization` для ping помечен sensitive. Утечек токена/пароля в логи и ошибки не найдено, кроме `describe()` (P1-16) и прокси/хаба (P1-13).
- **Подпись обновлений:** Ed25519 привязана к `bebra-update:<версия>:<sha256>`; старый установщик под новый тег не проходит (тест `signatures_bind_version_and_file`); лимиты размера есть. Повторная проверка перед запуском — P2-27.
- **Пакеты:** пакет может содержать только `Locale/<lang>/*.ftl`; `..`, `\`, `:`, ведущий `/`, control-символы и посторонние файлы отклоняют пакет целиком; на диск по путям из пака ничего не пишется; zip-slip фактически невозможен.
- **Модули:** `unpack_zip` использует `enclosed_name` + `Component::Normal` — zip-slip закрыт (гонка установки — P1-9).
- **UI-безопасность:** `{@html}` нигде нет; `open_url` проверяет `http(s)` и длину; цвета своей темы валидируются регуляркой; шрифт чистится; XSS/CSS-инъекцию через тему найти не удалось.
- **Tauri:** CSP строгая (`default-src 'self'`, connect только ipc), capabilities минимальны (`allow-listen`/`allow-unlisten`), токены в UI не передаются.
- **content.db:** схема и имена миграций соответствуют официальному лаунчеру, `PRAGMA journal_mode=WAL`, Loader читает её напрямую; схему не меняли.
- **Настройки:** `.bak`, карантин битого файла и восстановление уже есть (не хватает санитайзинга при чтении — P1-19).
- **i18n:** тест сверяет ключи и плейсхолдеры четырёх локалей; расхождений и пустых значений нет.
- **`docs/IMPROVEMENTS.md`:** B01 (время при `close_on_play`), B04 (refresh), B05 (фокус), B06 (RunningClient) уже закрыты или частично закрыты; B07 указывает на неиспользуемую функцию.

## 10. Что не проверялось

- `dotnet build`/`dotnet publish` Loader, предупреждения компилятора C#.
- Живая сеть: хаб, auth, CDN, серверы, redial, `ss14://`.

- Релизный цикл `scripts/release.ps1` (подпись, публикация, установка обновления).

- Конкретные версии Rust-крейтов с crates.io (офлайн); MSRV не зафиксирован.
- Поведение Robust при повторных `--connect-address`/`extra_args` (P1-15) — вывод по коду лаунчера, не по клиенту.
- Точные лицензии нативных библиотек из `Robust.Natives` (P2-77).
