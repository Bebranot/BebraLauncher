# Правила: журнал изменений и версии

**Обязательное правило: любое изменение, которое увидит пользователь лаунчера, записывается в [CHANGELOG.md](../CHANGELOG.md) в том же коммите, где оно сделано. Выпуск без записи в журнале невозможен: `scripts/release.ps1` откажется — не найдёт раздела для версии, увидит пустой текст или непустой `## [Не выпущено]`.**

Это правило для всех, кто правит проект, включая ассистента (Claude): перед коммитом проверить, не нужна ли строка в журнале.

## Версии: `a.b.cdd`

| Часть | Что значит | Пример |
| --- | --- | --- |
| `a` | глобальные, масштабные изменения | новый движок интерфейса, смена всей работы лаунчера |
| `b` | значительные, но не глобальные | новая вкладка, редизайн, новая большая возможность |
| `c` | между значительными и мелкими патчами | заметная доработка существующей возможности, пара исправлений разом |
| `dd` | микро-патчи, совсем не значительные | опечатка, мелкая правка вида, исправление одной мелочи |

Версия показывается как `0.2.305`: `a` = 0, `b` = 2, `c` = 3, `dd` = 05. `c` это одна цифра (0–9), `dd` две (00–99).

**Как хранится.** Cargo, Tauri и npm требуют вид `a.b.patch`, поэтому в файлах пишется `patch = c*100 + dd` без нулей впереди: версия `0.2.305` это `0.2.305`, а `0.2.005` это `0.2.5`. Лаунчер сам показывает её с тремя цифрами. Число патча не больше 999.

Когда растёт старшая часть, младшие обнуляются: после `0.2.305` значительное изменение даёт `0.3.000`, глобальное `1.0.000`.

Версия записана в трёх местах, и они должны совпадать (это проверяет тест):

- `Cargo.toml`, раздел `[workspace.package]`, поле `version`;
- `app/src-tauri/tauri.conf.json`, поле `version`;
- `app/package.json`, поле `version`.

## Журнал

Файл `CHANGELOG.md` в корне. Новые записи сверху.

```
## [Не выпущено]

### Добавлено
- ...

## [0.2.001] — 2026-10-05

### Исправлено
- ...
```

- Группы: **Добавлено**, **Изменено**, **Исправлено**, **Удалено**, **Безопасность**. Пустые группы не пишутся.
- Запись для человека: что стало иначе, простыми словами, одной-двумя строками. Без имён внутренних функций и без «рефакторинг», если пользователь ничего не заметит.
- Не нужны записи про тесты, документацию для разработчиков и внутреннюю уборку кода (если она ничего не меняет для пользователя).
- Заголовок версии: `## [a.b.cdd] — ГГГГ-ММ-ДД`, номер с тремя цифрами после второй точки.

## Как вести

1. Сделал изменение, видимое пользователю: добавил строку в раздел `## [Не выпущено]` (создать, если его нет, он стоит выше всех версий). Это в том же коммите.
2. Готовишь выпуск:
   1. Выбери номер по таблице выше (по самому крупному из накопленных изменений).
   2. Переименуй `## [Не выпущено]` в `## [номер] — дата`.
   3. Поставь тот же номер в трёх местах (см. выше).
   4. Закоммить и запушь.
   5. Запусти `scripts/release.ps1`: он соберёт установщик, подпишет его и опубликует релиз на GitHub; текст релиза берётся из журнала. Лаунчеры у пользователей найдут его на вкладке «Обновления».
3. Журнал показывается в самом лаунчере (вкладка «Обновления»), поэтому он обязан быть читаемым.

## Что проверяют тесты

(`app/src-tauri/src/changelog.rs`, запускаются обычным `cargo test`.)

- самая новая версионная запись журнала совпадает с версией сборки;
- версии записей корректны, идут от новых к старым, у каждой есть дата и хотя бы одна строка;
- раздел «Не выпущено», если есть, стоит выше всех версий;
- версия в `Cargo.toml`, `tauri.conf.json` и `package.json` одна и та же.

Тесты НЕ проверяют, что раздел «Не выпущено» пуст, и не мешают выпуску. Это делает `scripts/release.ps1`: он падает, если в этом разделе остались строки, если нет раздела с номером текущей версии или если его текст пуст. То есть правило выше обеспечивает именно релизный скрипт, а не `cargo test`.

Если тест падает после поднятия версии: не хватает записи в журнале или версия поменяна не везде.
